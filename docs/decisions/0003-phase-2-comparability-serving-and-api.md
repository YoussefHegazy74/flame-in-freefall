# ADR 0003: Comparability, Serving States, and the Read-Only API

**Date:** 2026-11-09
**Status:** Accepted
**Phase:** 2

## Context

Phase 1 produced 13 canonical Parquet tables with provenance, units, quality flags, and a reproducible dataset version. The next step had to expose those tables without turning a name match, a shared column, or a chart request into a scientific claim. The platform also had to distinguish "the file exists" from "this use is scientifically allowed."

## Decisions

### 1. Comparability is an explicit registry

Every measurement that may participate in a comparison is registered with its dataset, physical quantity, unit, unit status, value kind, calibration status, availability, and source references. Every allowed or forbidden pair is an explicit rule.

Consequences:

- An unregistered pair defaults to `not_comparable`.
- The engine downgrades or blocks a rule when units differ without a declared conversion, value kinds differ, either side is uncalibrated, or the physical quantity differs.
- Conditions are named booleans. Missing conditions produce `conditionally_comparable`; a false condition produces `not_comparable`.
- The API returns the decision as a normal `200` response.

### 2. Serving state is use-specific

Serving state is evaluated at dataset and measurement level for four uses: `exploration`, `quantitative_comparison`, `time_series`, and `provenance`.

Consequences:

- A dataset can be browsable but blocked for quantitative comparison.
- A downloaded file does not imply a servable measurement.
- Metadata-only records never render as zero-valued data.
- Every response carries the state, reasons, restrictions, and warnings that apply.

### 3. DuckDB is a bounded, named-query layer

The analytical layer exposes named operations over read-only views of canonical Parquet. It never accepts SQL, table names, paths, or free-form filters from a client. Pages and series are bounded. Series requests are rejected with `413` rather than silently downsampled. A watchdog interrupts queries that exceed the time budget.

### 4. The API is read-only and strict

FastAPI serves the registry and bounded queries. Query parameters are allowlisted, unknown or repeated parameters are rejected, errors use one envelope, request IDs are propagated, and CORS is environment-driven. The API does not expose write endpoints, arbitrary paths, or assistant endpoints in Phase 2.

### 5. Registry artifacts are committed and reproducible

`data/metadata/comparability_registry.json` and `data/metadata/serving_registry.json` are generated by `scripts/build_phase2_registries.py`. The script supports `--check` so the committed artifacts can be verified without rewriting them.

## Alternatives considered

| Alternative | Why rejected |
|---|---|
| Infer comparability from field names | Violates the scientific rules; names are not definitions. |
| Compare any two numeric columns with a unit conversion | Ambiguous units, measured/computed conflicts, and calibration limits would be hidden. |
| Treat download status as serving status | A present file can still be uncalibrated, ambiguous, or out of scope. |
| Expose raw SQL through the API | Cannot bound queries, cannot guarantee read-only access, and leaks the storage layout. |
| Downsample oversized series silently | Changes the data without telling the user. |
| Return an HTTP error for a blocked comparison | Hides a valid scientific decision behind a transport failure. |

## Consequences

Positive:

- Every comparison and serving decision is reviewable in versioned JSON.
- The API cannot invent a comparison or silently convert a unit.
- The frontend has explicit states to render.
- Tests cover every state and every hard restriction.

Negative:

- Registry maintenance is manual and must be reviewed when a new measurement is added.
- The API surface is narrower than the target contract: no citations, files, fields, publications, facets, assistant, ETag, or rate limiting yet.
- The material route is `/material/tests` while the target contract uses `/materials/tests`; this must be reconciled before the frontend is built.
